STM32F7 and Networking
======================

This is a proof of concept. It runs, and everything claimed below was measured
on the board rather than reasoned about, but it was written to find out whether
the thing could be done, not to be the final shape of it. What follows is
written for whoever takes it further.

### What runs

A NUCLEO-F746ZG answers `ping` and sends one. BusyBox `ping` works from the
board's own shell. The core runs at 216 MHz with both caches on.

    make nucleo_f746zg_defconfig
    ./scripts/download-stm32f7-libs.sh
    make
    make flash

The console is on USART3, which the debugger on the far end of the board
carries to the host as a virtual COM port -- nothing to wire. `Kconfig` offers
two alternatives that leave the terminal on a pin header instead, for a
converter of the reader's own; see "The console" below.

### The board

* [NUCLEO-F746ZG](https://www.st.com/en/evaluation-tools/nucleo-f746zg.html) (STM32F746ZG, Cortex-M7)
  - Select with `make nucleo_f746zg_defconfig`
  - USART3 (console): PD8 (TX), PD9 (RX) -- carried to the host by the debugger
  - LEDs: PB0 green, PB7 blue, PB14 red
  - Ethernet: LAN8742A at address 0, RMII

The clock comes from the debugger rather than a crystal of the board's own: 8
MHz in, bypassed rather than driven, multiplied to 216 MHz. `platform/system_stm32f746.c`
does this before the kernel starts, because the kernel reads the rate it ended
up at when it sets its timer and there is no hook of the board's own that runs
early enough.

### What is new and what was only parameterised

The context switch was not touched. `kernel/arch/v7m_entry.S` is the same file
the Cortex-M4 boards use, including the half of the floating point unit the
scheduler has to carry itself: it is written against ARMv7-M, which is what
both cores are.

`makefiles/common.mk` was parameterised with `?=` so a board can say what it
has. Every default is what the older family had, so those four boards build
byte for byte as before.

One call in `kernel/arch/v7m_port.c` changed: `NVIC_PriorityGroupConfig` became
`NVIC_SetPriorityGrouping`. That removes a dependency on the Standard
Peripheral Library rather than adding one, and means the same thing on both
families.

The line discipline that was inside the older serial driver is now
`drivers/periph/serial_tty.c` and both drivers share it. Nothing in it speaks
to a register.

### Networking

lwIP sits on the kernel through `net/lwip/sys_arch.c`, which turns what the
stack asks for into this system's threads, mutexes and semaphores.

A socket is a file. `kernel/socket_file.c` wraps a socket of the stack in a
file of this system and counts the descriptors that name it, the way a pipe is
counted, so `dup2` and `close` work on one without knowing what is behind it.
BusyBox `ping` needs exactly that: it moves its socket onto descriptor 0.

Everything the stack is asked to do happens in the thread that asked. The
kernel keeps only the book. This is not a preference: every way this kernel
lets a thread wait is a system call, a system call is a supervisor instruction,
and a supervisor instruction inside the handling of one is a fault. A socket
call made from inside a system call faults on the first lock the stack takes.

### Known limitations

* **Frames are collected by polling, not by the interrupt.** For the same
  reason as above: there is nothing an interrupt could say here that a thread
  could be waiting for. The interval is 1 ms and is set in
  `drivers/net/ethernetif.c`. Claiming the interrupt needs the controller to
  have an interface of its own in the file system, waited on the way a terminal
  is.

* **The address table is filled from the packets themselves.** On the segment
  this was built against, the gateway answers ARP for every address on it, so
  asking who holds a neighbour's address returns the gateway and a reply sent
  there goes no further. `arp_learn()` in `drivers/net/ethernetif.c` believes
  what arrived instead. The entries it makes are fixed ones and do not age,
  because that is the only kind the stack lets anything outside it make. On a
  segment without a gateway that answers for everyone, this can go.

* **Name resolution is configured but was never exercised.** The server is set
  and the calls are linked; no name has been looked up. `nslookup` is the
  smallest thing that would say.

* **Counters and frame snapshots are still in `drivers/net/eth.c`.**
  `eth_stat_*` and `eth_peek_*` were added to find a checksum being overwritten
  and are worth keeping only as long as something is being chased.

* **The heap is small.** 20 KB of user heap and 64 KB of page memory, of 320 KB.
  The defaults came from the older boards and nobody has revisited them.

### The caches, and why the MPU is there

Both caches are on. On a workload that is BusyBox interpreting a shell loop --
measured inside the firmware, so no terminal is in the way -- that is 1.57x.

The data cache is why the MPU is programmed. The Ethernet controller reaches
memory as a bus master and knows nothing of the copy the core keeps. The other
way to keep the two in step is to clean and invalidate by hand around every
transfer, and that is not available here: those are privileged instructions and
the driver runs in an unprivileged thread.

So `platform/system_stm32f746.c` describes four regions and marks one of them
uncached. Not to protect anything -- the threads of this system share one
address space -- but because the unit that says what may be cached is the same
unit that says what may be reached. Every region allows everything.

Two things follow that are easy to get wrong:

* **Anything a bus master will read or write must be in the `.eth_dma`
  section.** Memory from the page allocator must never be handed to the
  controller, and not only because of the cache: that allocator lives entirely
  within the first 64 KB, which is tightly coupled to the core and is not on
  the bus matrix at all.

* **The section is 8 KB and the region cannot be told a length that is not a
  power of two.** Should the section outgrow it, the region would go on
  covering the first half and the rest would be cached, shared, and wrong in a
  way nothing reports. The linker script stops the build instead. Grow both
  together.

### What was found on the way

Four things were broken and are fixed. Three belong to this port; the last does
not.

* The controller was recomputing checksums over frames that already carried
  correct ones, and writing something that was neither. The frames went out and
  the far end discarded them without a word. `ETH_CHECKSUM_DISABLE` is now
  asked for explicitly, which is the only way to have the library write that
  field at all.

* The management wires were being clocked past what the transceiver allows,
  because the library does not set that rate itself and nothing had asked it
  to.

* The controller was being told the terms of a link that had not finished being
  agreed, and settled on half duplex against a full duplex far end.

* `kernel/kernel.c` was staging `sigev_notify_function` as the handler when a
  timer expired with `SIGEV_SIGNAL`. POSIX has that mode name a signal, not a
  function; naming a function is what `SIGEV_THREAD` does. A caller that filled
  in the signal and left the function empty -- which is what `alarm()` does --
  had the kernel jump to nothing. This has nothing to do with this family and
  is fixed where it was.
